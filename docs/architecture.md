# 架构与行为边界

公共套件负责流程、forge 接口与权限，项目目录负责业务规则、验证命令和资源，执行方适配器负责 agent 产品的任务及安装格式。

## 配置与渲染

配置入口接收项目目录或 TOML 文件。目录方式读取 `project.toml`，加载可选规则覆盖并按角色复制 hooks/assets。单文件方式只读取配置。`kit` 校验必填字段、凭据引用、路径和工作流，渲染器用同一工作流生成执行规则、评审标准、分派说明和评审复核入口。

生成目录分为 `reviewer/`、`fixer/`。运行组件读取 `AGENT_REVIEW_CONFIG` 或自身附近的 `project.toml`。模板缺参在渲染时失败；渲染先在暂存目录完成，再替换受管输出，避免失败后留下半套新文件。

## Forge 与凭据

`kit.forge` 将 GitLab 与 GitHub 的条目、评论、标签、变更、成员、合入和文件提交统一。GitHub PR 拉取使用 `refs/pull/<编号>/head`，支持 fork；GitLab 使用配置的源分支引用前缀。

`kit.transport` 在进程内读取凭据，可直接请求或经配置的 SSH 链请求。凭据不放入命令参数，错误信息不回显 token 或远端响应正文。导入评审 CLI 不读取凭据或发起请求。

## 评审调度

轮询先检查已合入条目，再检查成员同意和自动合入，随后选取待评审项。完整评审由执行模型起草、独立模型复核；评论回复和无新提交的 MR 可使用轻量路径。已有仅文字修改结论的 issue 也可进入轻量检查，系统评论不作为依据。

`slot-<编号>.lock` 控制并发，条目锁阻止同时处理同一对象，`state.lock` 保护状态读写，`prep.lock` 串行准备 Git 工作区。`merge.lock` 与 `register.lock` 分别串行合入和登记。变化标识包含更新时间、MR SHA 或评论 ID；同一标识达到尝试上限后停止，新变化可再次触发。

静默期、每小时启动上限、尝试次数、超时和预算来自 `reviewer.limits`。用户评论优先，暂停文件阻止自动轮询。评审 `--dry-run` 会保留本地状态和事件但禁止 forge 写入；登记 `--dry-run` 只输出计划，不创建状态或事件。

## 工作流与证据

`workflow.verify` 的类型及路径条件决定适用验证，`run` 和内建步骤描述执行方需要提供的证据。评审方仅重跑配置为复核的步骤，使用 `reviewer_run` 或 `run`。命令失败、输出缺失和环境不满足都必须保留为评审证据，不能据此宣称验证通过。

`workflow.metrics` 提供复杂度命令与测试比例限制。项目 hook 处理部署、专用硬件或其他业务验证；公共套件不内置某一项目的部署命令、文件结构或登记 schema。

## 合入与登记

合入要求有效成员同意、评审可合入和 forge 可合入状态。最近有效撤回会取消同意；机器人和执行、评审身份不参与成员同意。最终请求带当前 HEAD，避免检查与请求间的提交变化。冲突交回执行方追加修复并重评。成功合入先保存通知状态，评论失败后下一轮补发。

登记从目标分支快照生成变更，使用稳定条目标识去重。通用 changelog 记录合入结果；项目 hook 通过显式路径白名单写入业务文件。所有文件放在一次提交中，GitLab 带文件版本，GitHub 非强制更新 ref。分支变化或 API 失败时停止本轮，保持未登记供后续重试。

## 安装与适配器

评审安装器更新项目专属文件及带 `# agent-review-loop:<项目名>` 标记的 cron 行，登记使用独立标记。Hermes 安装器只合并审批、委派和 `agent.max_turns`，按任务名维护分派、通知、清理任务。同一 Hermes home 不能覆盖不同项目，需使用独立 home/profile。适配器详细输入输出见[契约](adapters.md)。
